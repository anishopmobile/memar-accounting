# بررسی امنیتی حسابداری معمار — ۱۴۰۵/۰۷/۳۰ (۲۰۲۶-۱۰-۲۲)

## دامنه
بازبینی استاتیک نقاط پرخطر مرتبط با احراز هویت، نشست و محدودیت ورود، تنظیمات دیتابیس، API پشتیبان/بازیابی، ذخیره‌سازی تصاویر و آپلودهای کاربر؛ همراه با تست‌های خودکار موجود (PHP lint، JavaScript، سناریوهای واقعی HTTP، MariaDB/MySQL، mPDF و مرورگر).

این بررسی **معادل آزمون نفوذ مستقل روی تنظیمات واقعی سرور یا ممیزی کامل کد خط‌به‌خط نیست**. امنیت نهایی به پیکربندی هاست، سطح دسترسی دیتابیس و مرور سایر ماژول‌ها نیز وابسته است.

## رفع‌شده در شاخه `security/hardening-audit-20261022`

1. **جعل IP در ورود:** هدرهای `X-Forwarded-For` و `Client-IP` دیگر به‌طور پیش‌فرض قابل اعتماد نیستند؛ مبنا `REMOTE_ADDR` است. فقط IP پراکسی مشخص‌شده در متغیر `MEMAR_TRUSTED_PROXIES` می‌تواند هدر `X-Forwarded-For` با یک IP معتبر را ارائه دهد؛ زنجیره‌های مبهم رد می‌شوند. تنظیم اشتباه پراکسی ممکن است محدودسازی IP را به IP پراکسی اعمال کند.
2. **اطلاعات اتصال دیتابیس:** `MEMAR_DB_HOST`, `MEMAR_DB_USER`, `MEMAR_DB_PASSWORD`, `MEMAR_DB_NAME` قابل خواندن از محیط وب‌سرور/هاست هستند و نام دیتابیس اعتبارسنجی می‌شود؛ خطای اتصال و اطلاعات داخلی فقط در لاگ سرور ثبت می‌شوند و به کاربر نمایش داده نمی‌شوند. پیش‌فرض قدیمی برای سازگاری حفظ شده و باید روی سرور جایگزین شود.
3. **محل ذخیره پشتیبان:** مسیرهای نسبی اکنون **بیرون از DOCUMENT_ROOT** در `memar-private-backups` ایجاد می‌شوند. مسیر مطلق درون ریشه عمومی پروژه یا ریشه وب‌سرور رد می‌شود، حتی اگر از لینک نمادین یا مسیر `..` استفاده کند. تنظیمات قدیمی داخل پوشه عمومی تا تغییر مسیر قابل استفاده نخواهند بود.
4. **فایل‌های لینک‌شده در پشتیبان:** بکاپ کامل فایل‌ها، لینک‌های نمادین را دنبال نمی‌کند و از نسخه‌برداری فایل‌های محیطی `.env` و فراداده `.git` پرهیز می‌کند. حذف پوشه `files` قبلی نیز لینک نمادین را دنبال نمی‌کند؛ اگر خود پوشه `files` symlink باشد، عملیات رد می‌شود.
5. **فایل بازیابی SQL:** لازم است آپلود واقعی HTTP با اندازه مثبت و حداکثر ۲۰۰ مگابایت باشد. وضعیت CSRF و الزام ورود که از قبل وجود داشتند حفظ شدند.
6. **نشست و هدرهای مرورگر:** نشست strict/cookie-only شده و هدرهای `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin` افزوده شده است.

## کارهای ضروری هنگام استقرار (با هماهنگی مدیر هاست)

- یک **کاربر اختصاصی MySQL با حداقل سطح دسترسی موردنیاز اپلیکیشن** بسازید؛ تنظیمات قدیمی `root` و رمز خالی را برای محیط عملیاتی کنار بگذارید. مقدار این متغیرها را در تنظیمات محرمانه هاست بگذارید، **نه داخل پروژه/گیت یا پوشه قابل دانلود**. توجه کنید که اپلیکیشن فعلاً روی درخواست‌های معمول migration/DDL انجام می‌دهد؛ پیش از کاهش مجوزها نیاز است چرخه migration در محیط staging ارزیابی شود.
- استفاده از HTTPS، عدم انتشار صفحه خطاها، دسترسی محدود به لاگ‌ها، تنظیم وب‌سرور برای **عدم اجرای PHP در پوشه آپلود** و عدم انتشار پشتیبان‌های قدیمی از پوشه عمومی را با مدیر هاست بررسی کنید. تغییر محل پشتیبان جدید، فایل‌های قدیمیِ ایجادشده در مسیر عمومی را به‌صورت خودکار حذف نمی‌کند.
- اگر reverse proxy دارید، `MEMAR_TRUSTED_PROXIES` را فقط به **IP واقعی و کنترل‌شده آن پراکسی** (با کاما) محدود کنید و پراکسی حتماً X-Forwarded-For دریافتی کاربر را overwrite کند. بدون پراکسی مقدار را تنظیم نکنید.
- یک پشتیبان معتبر خارج از وب‌روت و نسخه آزمایشی برای تست بازیابی کامل نگه دارید. عملیات بازیابی SQL همچنان یک اقدام مخرب مدیریتی است؛ ریسک ناشی از اشتباه کاربر، SQL قدیمی ناسازگار یا خرابی هاست با اعتبارسنجی آپلود به‌طور کامل از بین نمی‌رود.
- هرگونه ارتقای بعدیِ مجوزهای نقش‌ها، MFA، گزارش دسترسی‌ها، جداسازی migration از درخواست‌های مالی و بازنویسی امن parser فایل SQL به یک توسعه جداگانه همراه با سناریوهای سازگاری مالی نیاز دارد.

## کنترل‌های پذیرش

- تست spoofed XFF در حالت عادی و پراکسی معتبر، کنترل ذخیره نکردن پشتیبان در `DOCUMENT_ROOT` و امکان تهیه پشتیبان در مسیر خصوصی.
- آزمون‌های قبلی محصولات، فاکتور، برگشت، مالی، ارز، گالری، PDF، بکاپ و بازیابی ZIP.
- بررسی دستی هاست: وضعیت TLS، سطح دسترسی DB، محل ذخیره فایل‌ها، و عدم دسترسی URL به SQL/ZIP و پوشه‌های آپلود.
